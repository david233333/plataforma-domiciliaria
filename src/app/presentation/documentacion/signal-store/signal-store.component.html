1. Qué es y por qué

Punto de partida: los signals de Angular

Un signal es un contenedor reactivo de un valor: cuando cambia, todo lo que lo lee (el template, un computed, un effect) se actualiza solo. 

{{ code.signalsRecap }}

Eso resuelve la reactividad de un valor. El problema aparece con muchos valores relacionados, lógica derivada y operaciones asíncronas: acabas con un servicio lleno de signals sueltos, subscribe() manuales y limpieza de suscripciones a mano. Ahí entra el SignalStore.

El SignalStore

signalStore(...) es una factoría que construye un servicio Angular (una clase inyectable) cuyo estado son signals. No es un store global tipo Redux: es un contenedor de estado componible. En vez de escribir la clase a mano, la ensamblas con "features". 

{{ code.storeShape }}

Tipado y central

Una sola forma del estado; cada campo es un signal de solo lectura.

Escritura controlada

La UI no muta nada por la espalda: solo los métodos del store cambian el estado.

RxJS integrado

Lo asíncrono con rxMethod y auto-limpieza de suscripciones.

2. Las "features": estado, derivados y acciones

Cada feature aporta una parte, y las siguientes ven lo que aportaron las anteriores (los computed leen el estado; los métodos leen estado y computed).

withState(initialState) — el estado

Define la forma del estado. Cada propiedad se convierte en un signal de solo lectura. 

{{ code.withStateSnippet }}

withComputed(...) — lo derivado

Son computed() que se recalculan solos al cambiar sus fuentes. Evitan duplicar lógica en los templates. 

{{ code.withComputedSnippet }}

withMethods(...) — las acciones

La única vía para cambiar el estado. Aquí inyectas dependencias (servicios, casos de uso) en los parámetros por defecto. 

{{ code.withMethodsSnippet }}
Existe además withHooks({{ '{' }} onInit, onDestroy {{ '}' }}) para enganchar el ciclo de vida del store. En este proyecto la carga inicial se hace desde el constructor del componente, así que no se usa.

4. rxMethod y tapResponse — lo asíncrono

rxMethod (de @ngrx/signals/rxjs-interop)

Crea un método reactivo a partir de un pipe de RxJS. Lo llamas como una función normal y él gestiona la suscripción y la limpia cuando el store se destruye (adiós al takeUntilDestroyed / subscribe manual). 

{{ code.rxMethodSnippet }}

tapResponse (de @ngrx/operators)

{{ code.tapResponseSnippet }}
Regla de oro: si un error llega hasta el rxMethod, el método deja de reaccionar a futuras llamadas. Por eso tapResponse captura next/error dentro del stream y la cadena reactiva sigue viva.

5. Dónde se provee: global vs por pantalla

{{ code.provideSnippet }}
Este proyecto usa el estado por pantalla: el store se registra en los providers del componente página, así nace y muere con la pantalla. Cada vez que entras a «Nueva solicitud» empiezas limpio, sin resets manuales.
