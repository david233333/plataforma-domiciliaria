Cómo funciona el sistema de estilos

Una sola fuente de verdad, cinco capas que cooperan y un orden de cascada explícito. Aquí está todo el circuito: quién carga qué, qué hace main.scss y cómo decides dónde escribir cada estilo.

00 La idea central: una sola fuente de verdad

Antes de las capas, entiende la regla que las une todas: cada decisión de diseño (color, espacio, radio, sombra) se define UNA vez como un token --app-*. Todo lo demás solo lo consume.

Los tokens viven en src/styles/tokens/ como variables CSS en :root:

/* tokens/_spacing.scss y _colors.scss → :root */
--app-primary-600: #2563eb;   /* azul de marca */
--app-space-4:     1rem;      /* 16px */
--app-radius-md:   0.375rem;  /* 6px — radio por defecto */
--app-shadow-xs:   ...;       /* sombra sutil de card */
¿Por qué importa? Si mañana el azul de marca cambia, lo tocas en un solo archivo y se actualizan Tailwind, los componentes de PrimeNG, los patterns y el CSS de cada componente a la vez. Nadie hardcodea #2563eb en ningún lado.

01 ¿Quién carga todo, al final?

El que “llama” a los estilos no es Angular ni un componente: es angular.json. Ahí se declara, en orden, qué CSS entra al bundle.

// angular.json → architect.build.options.styles[]
"styles": [
  "node_modules/primeicons/primeicons.css",  // 1º  íconos pi-*
  "src/styles/tailwind.css",                // 2º  Tailwind + @theme
  "src/styles/main.scss"                    // 3º  nuestro orquestador
]

Ese orden produce este flujo de entrada al navegador:

1 · primeicons.css
La tipografía de íconos pi pi-home, pi pi-bell…
▼
2 · tailwind.css (es .css a propósito)
@import "tailwindcss" + el plugin de PrimeUI + @theme inline que conecta los tokens. Aquí Tailwind emite su @layer base y @layer utilities.
▼
3 · main.scss
Declara el orden de capas y “rellena” tokens, reset, tipografía, tema PrimeNG, layout, patterns y animaciones.
¿Por qué tailwind.css es .css y no .scss? Porque @import "tailwindcss" es una directiva de PostCSS, no de Sass. Si la procesara el compilador Sass, rompería la build.

02 Qué hace main.scss (el orquestador)

No contiene estilos visuales propios: su trabajo es cargar todo en el orden correcto con @use. El orden es crítico — un token debe existir antes de que alguien escriba var(--app-*).

@use 'abstracts/layers';        // 1. Declara @layer ANTES que nada
@use 'tokens/colors';           // 2. Tokens en :root (la fuente de verdad)
@use 'tokens/typography';       //    ...deben existir antes de usarse
@use 'tokens/spacing';
@use 'tokens/elevation';
@use 'tokens/motion';
@use 'base/reset';             // 3. Reset mínimo (@layer reset)
@use 'base/base';              //    defaults globales
@use 'typography/typography';   // 4. Clases .text-* (@layer components)
@use 'themes/primeng-theme';    // 5. --p-* = var(--app-*) (@layer sp-theme)
@use 'layout/containers';       // 6. container-*, section (@layer layout)
@use 'patterns/patterns';       // 7. .card .field .status-badge (@layer components)
@use 'utilities/animations';    // 8. keyframes fadeIn / shimmer (@layer utilities)
Piensa en main.scss como el índice de un libro: no cuenta la historia, pero define en qué orden se leen los capítulos para que todo tenga sentido. Si pones el capítulo de tokens después de quien los usa, el libro no se entiende (los var(--app-*) saldrían vacíos).

03 @layer: el orden de la cascada

Este es el concepto que hace que todo conviva sin guerras de !important. Una capa posterior siempre gana sobre una anterior, sin importar la especificidad del selector.

El orden se declara en una sola línea (abstracts/_layers.scss), y es la primera línea de CSS que llega al navegador:

@layer reset, base, primeng, sp-theme, layout, components, utilities;

Visto como prioridad (abajo = más fuerte):

resetNormalizaciones mínimas propias— menor prioridad
baseAquí aterriza el preflight de Tailwind (el nombre coincide a propósito)
primengLos estilos de los componentes de PrimeNG
sp-themeNuestros overrides --p-* = var(--app-*) → ganan a PrimeNG sin !important⬅ por eso va encima
layoutcontainer-*, section
componentsLos patterns: .card .field .status-badge
utilitiesAquí aterrizan las utilidades de Tailwind → máxima prioridad⬅ mayor prioridad
↑ gana en la cascadala primera capa pierde ↓
Consecuencia práctica: como utilities (Tailwind) es la capa más alta, si pones class="p-2" en un .card (que define padding en components), Tailwind gana y ajusta el padding. Por eso el layout puntual siempre puede sobrescribir al pattern desde la plantilla.
El detalle que no se puede romper: este mismo orden se repite en app.config.ts → providePrimeNG({ cssLayer: { order: 'reset, base, primeng, sp-theme, layout, components, utilities' }}). Si los dos órdenes difieren, PrimeNG inyecta fuera de capa y se rompe toda la cascada.

04 Cómo los tokens se vuelven utilidades de Tailwind

Tailwind v4 es CSS-first: no hay tailwind.config.js. La configuración vive en tailwind.css con @theme inline, que mapea los tokens a las utilidades.

/* tailwind.css */
@theme inline {
  --color-text-secondary: var(--app-text-secondary);
  --spacing-4:            var(--app-space-4);
  --radius-xl:            var(--app-radius-xl);
}

Eso hace que estas utilidades existan conectadas al token:

Escribes en el HTML
class="text-text-secondary p-4 rounded-xl"
▼
Tailwind genera CSS que apunta al token
color: var(--app-text-secondary); padding: var(--app-space-4); …
▼
Resultado en pantalla
El valor real del token. Cambia el token → cambia la utilidad.
inline es la palabra clave: hace que Tailwind no cree sus propias variables, sino que inyecte directamente var(--app-*). Así nunca hay dos fuentes de verdad ni referencias circulares.

05 El puente con PrimeNG

Los componentes de PrimeNG (botones, selects, drawer…) se estilan con sus variables --p-*. El truco: hacemos que --p-* = var(--app-*), así heredan nuestra marca automáticamente.

1. Estado inicial — en app.config.ts se define un preset (basado en Lara) con valores HEX directos, para que PrimeNG ya se vea bien antes de que cargue el SCSS.

// app.config.ts
definePreset(Lara, {
  semantic: { primary: {
    600: '#2563eb', ...
  }}
})

2. Vínculo real — en _primeng-theme.scss (@layer sp-theme) re-apuntamos cada --p-* al token. Como sp-theme va encima de primeng, gana sin !important.

// themes/_primeng-theme.scss
--p-primary-color: var(--app-primary-600);
--p-button-...:   var(--app-...);
Regla: si necesitas cambiar el aspecto de un componente PrimeNG (.p-button, .p-select), NO lo hagas en el styles del componente Angular → va en _primeng-theme.scss, dentro de @layer sp-theme.

06 La escalera de decisión

Cuando vas a estilar algo, bajas por esta escalera y te detienes en el primer escalón que resuelva tu caso. El CSS scoped es el último recurso.

1

Tailwind en la plantilla 90% de las veces

Layout, spacing, responsive: flex, grid, gap-4, mb-8, lg:grid-cols-3. Mapeado a tokens.

2

Clase tipográfica texto

Todo lo que sea texto: text-heading-xl, text-body-lg, text-overline. Empaquetan tamaño + peso + color.

3

Pattern pieza repetida

Algo que se repite en varias pantallas con decisiones de marca/accesibilidad: .card, .field, .status-badge, .empty-state, .skeleton.

4

Tema PrimeNG override de PrimeNG

Cambiar un componente de la librería → _primeng-theme.scss (@layer sp-theme). Nunca en el componente.

5

CSS scoped del componente último recurso

SOLO lo que nada de lo anterior cubre y es exclusivo de este componente: @keyframes, gradientes, pseudo-elementos ::before, :host, reset de un elemento nativo.

Termómetro: si el bloque styles de un componente pasa de ~30–40 líneas, casi seguro hay layout o colores que debían ser Tailwind/tokens.

07 Anatomía de un componente real

Un mismo bloque de HTML mezcla las capas. Cada clase viene de un “proveedor” distinto, y todas conviven gracias al orden de @layer.

<form class="card max-w-xl flex flex-col gap-5">

  <div class="field">
    <label class="field__label">
      Identificación <span class="field__required">*</span>
    </label>
    <input pInputText class="w-full" />   <!-- estilo del input: tema PrimeNG -->
    <span class="field__message-slot"> … </span>
  </div>

  <h2 class="text-heading-md m-0">Crear novedad</h2>
</form>

card field field__*Pattern (@layer components)Superficie/borde, estructura del campo, anti-layout-shift
flex flex-col gap-5 w-full m-0 max-w-xlTailwind (@layer utilities)Layout y spacing de ESTA pantalla
text-heading-mdTipografía (@layer components)Tamaño + peso + color del título
pInputTextTema PrimeNG (@layer sp-theme)Aspecto del input con la marca

08 Responsividad

Mobile-first, manejada por Tailwind en la plantilla, con breakpoints definidos una vez y compartidos con el SCSS.

En la plantilla → prefijos Tailwind. Sin prefijo = móvil; el prefijo es “desde este ancho hacia arriba”.

class="grid grid-cols-1
  sm:grid-cols-2
  lg:grid-cols-3
  xl:grid-cols-4"

1 col en móvil → 2 en sm → 3 en lg → 4 en xl.

En el SCSS → mixins. Cuando ya estás en CSS y Tailwind no aplica.

@include respond-to(md) { … }
  /* min-width: 768px */
@include respond-below(lg) { … }
  /* max-width: 1023.98px */

Los contenedores (container-app, container-fluid, container-narrow) ya encapsulan el ancho máximo + el padding lateral que crece con el viewport. No teclees esa ristra de utilidades cada vez.

09 El flujo completo, de punta a punta

Juntando todo: desde que defines un token hasta que un píxel aparece en pantalla.

① tokens/_*.scss
Defines --app-primary-600 una sola vez en :root.
▼
② Dos consumidores leen el token
a) tailwind.css vía @theme inline → utilidades.   b) _primeng-theme.scss → --p-* = var(--app-*).
▼
③ angular.json carga el CSS en orden
primeicons → tailwind.css → main.scss.
▼
④ main.scss orquesta con @use
Declara @layer y rellena reset, tokens, tipografía, tema, layout, patterns.
▼
⑤ @layer resuelve los conflictos
utilities (Tailwind) gana al pattern; sp-theme gana a PrimeNG. Sin !important.
▼
⑥ El componente combina capas
class="card flex gap-5" + field + text-heading-md + un poco de CSS scoped si hace falta.
▼
✓ Píxel en pantalla
Coherente, accesible y con la marca — y si cambias el token, todo se actualiza solo.
Resumen en una frase: los tokens son la verdad, angular.json los carga, main.scss los ordena, @layer decide quién gana, y tú solo eliges el escalón correcto (Tailwind → tipografía → pattern → tema → CSS scoped).
