  Por qué NO va en shared/

  El README.md de shared/ lo dice explícitamente:

  ▎ UI tonta (wrappers presentacionales de PrimeNG en ui/), pipes/, directives/ 
  ▎ y utils/ sin negocio. No depende de ninguna capa interna.

  shared/ es para piezas reutilizables y genéricas (un botón, un pipe de fechas,
  una directiva) que se usan en muchas pantallas. La regla mental es: "¿esto lo
  van a importar varios componentes?"

  Tu InicioComponent es lo contrario:
  - Es una página completa con ruta propia (/inicio), no un bloque reutilizable.
  - Tiene contenido específico del dominio ("Salud en Casa", la mascota, los
  highlights).
  - Nadie más lo va a importar — el router lo carga directo.

  Por eso presentation/inicio/ es exactamente donde debe estar, junto a tus
  otras páginas con ruta (novedades, notificaciones, documentacion,
  design-system). Es coherente con lo que ya tienes.

  Comparación rápida

  ┌──────────────────────┬────────────────────────────┬─────────────────────┐
  │       Carpeta        │         Qué va ahí         │   ¿Inicio encaja?   │
  ├──────────────────────┼────────────────────────────┼─────────────────────┤
  │ presentation/inicio/ │ Páginas/vistas con ruta    │ ✅ Sí — aquí está   │
  │                      │                            │ bien                │
  ├──────────────────────┼────────────────────────────┼─────────────────────┤
  │                      │ UI tonta reutilizable, sin │ ❌ No es            │
  │ shared/              │  negocio ni rutas          │ reutilizable ni     │
  │                      │                            │ genérico            │
  ├──────────────────────┼────────────────────────────┼─────────────────────┤
  │ core/                │ Servicios singleton, infra │ ❌ No es un         │
  │                      │  de app (auth, http, i18n) │ servicio            │
  └──────────────────────┴────────────────────────────┴─────────────────────┘

  Matiz: lo que sí podría salir hacia shared/

  Si en algún momento partes el InicioComponent y aparece una pieza genuinamente
  reutilizable —por ejemplo una <app-hero-card> o un <app-feature-list> que
  pienses usar también en otras pantallas— esa pieza sí iría en shared/ui/, y
  InicioComponent la consumiría. Pero hoy no hay nada reutilizable ahí: es todo
  contenido propio de la página de bienvenida.

  Recomendación

  Déjalo en presentation/inicio/. La única mejora "de nombre" que podrías
  considerar es llamarlo presentation/home/ si el equipo prefiere inglés, pero
  como tus rutas y labels están en español (/inicio, "Inicio"), inicio es lo más
  consistente.

  ¿Quieres que no toque nada (que es mi recomendación), o prefieres que extraiga
  alguna parte como componente reutilizable en shared/ui/?

  ├───────────────┼───────────────────────────────┼─────────────────────────┤
  │ styles del    │ Solo lo que Tailwind NO cubre │                         │
  │ componente    │  bien (gradientes,            │ scoped en el .ts        │

  Qué es un "pattern" (y por qué existe)

  Un pattern es una receta de CSS con nombre, reutilizable, para una pieza de UI
  que se repite por toda la app con las mismas decisiones de diseño (color de
  marca, accesibilidad, estructura interna).

  Es el punto medio entre dos extremos:

  ┌───────────────────────────────────┬─────────────────────────────────────┐
  │              Opción               │              Problema               │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │ Repetir 8 utilidades Tailwind     │ Te equivocas en una, y los          │
  │ cada vez (flex flex-col gap-2     │ formularios quedan inconsistentes   │
  │ ...)                              │                                     │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │ Crear un componente Angular       │ Sobreingeniería: es CSS puro, sin   │
  │ <app-field>                       │ lógica                              │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │ Pattern (.field) ✅               │ Una clase, decisión tomada una vez, │
  │                                   │  idéntica en todos lados            │
  └───────────────────────────────────┴─────────────────────────────────────┘

  La regla del repo lo dice: "si Tailwind ya lo cubre con utilidades simples, NO
  se hace patrón". Solo se vuelve pattern cuando combina varias decisiones que 
  deben repetirse exactas.

  field = un campo de formulario completo

  Un "field" no es el <input>. Es todo el grupo: la etiqueta + el control + el
  mensaje de error/ayuda. Visualmente:

  Número identificación *        ← .field__label  (+ .field__required para el *)
  ┌──────────────────────────┐
  │  38478cd848b5            │   ← el control (un <input> de PrimeNG)
  └──────────────────────────┘
  ⚠ Este campo es obligatorio   ← .field__error  (o .field__hint para ayuda)

  En HTML se ve así:

  <div class="field">
    <label class="field__label" for="ident">
      Número identificación
      <span class="field__required">*</span>
    </label>

    <input pInputText id="ident" />

    <!-- Slot que SIEMPRE reserva el alto de una línea -->
    <span class="field__message-slot">
      @if (form.controls.ident.invalid) {
        <span class="field__error">Este campo es obligatorio</span>
      }
    </span>
  </div>

  Qué resuelve cada pieza

  - .field → solo apila verticalmente label/control/mensaje con un gap
  (flex-direction: column; gap). Nada más.
  - .field__label → fija la tipografía de TODAS las etiquetas (tamaño sm, peso
  medium, color de texto). Así todos los formularios tienen labels idénticas.
  - .field__required → el asterisco en rojo de marca (--app-error). Una
  decisión, un color, en todos lados.
  - .field__hint → texto de ayuda en tono muted.
  - .field__error → mensaje de error en rojo + un ícono ⚠ automático vía
  ::before (el content: '\e90c' es el triángulo de primeicons). No tienes que
  poner el ícono a mano.

  La parte clave: .field__message-slot

  Esta es la razón principal de que field sea un pattern y no utilidades
  sueltas:

  .field__message-slot {
    min-height: calc(var(--app-size-sm) * var(--app-leading-snug));
  }

  Reserva el alto de una línea de mensaje aunque esté vacío. ¿Por qué importa?
  Sin esto, cuando el usuario envía el formulario y aparece un error, ese texto
  "empuja" todo lo de abajo y la página da un salto (layout shift). Con el slot
  reservado, el espacio ya está ahí: el error solo se "rellena", nada se mueve.
  Eso es accesibilidad + pulido, y es justo el tipo de decisión que debe 
  repetirse idéntica en cada campo → por eso es pattern.

  Los demás, en una línea cada uno

  - status-badge → la "pastilla" de estado (GESTIONADA, PENDIENTE…). Encapsula
  el par fondo-claro + texto-oscuro con contraste WCAG verificado por cada color
  semántico. Lo viste en tu tabla de novedades.
  - empty-state → el bloque centrado de "no hay resultados" (ícono + título +
  texto muted).
  - skeleton → los placeholders grises con animación shimmer mientras carga.

  La regla mental para decidir

  ▎ ¿Esta pieza se repite en varias pantallas y combina color de marca / 
  ▎ accesibilidad / estructura que debe ser idéntica?
  ▎ - Sí → pattern (.field, .card…).
  ▎ - No, es layout de esta pantalla → Tailwind en la plantilla.
  ▎ - No, pero tiene lógica/estado → componente Angular.

  @Component({

      <form

    private readonly fb = inject(FormBuilder);

    protected readonly programas: OpcionPrograma[] = [
      { label: 'Plan de manejo', value: 'PLAN_MANEJO' },
      { label: 'Laboratorio', value: 'LABORATORIO' },
      { label: 'Enfermería', value: 'ENFERMERIA' },

    protected readonly enviado = signal(false);

    protected readonly form = this.fb.nonNullable.group({
      identificacion: [
        '',
        [Validators.required, Validators.pattern(/^\d+$/)],
      ],
      programa: ['', Validators.required],
      observacion: ['', Validators.maxLength(120)],
    });

    /** Un control es "inválido visible" solo si ya fue tocado o se intentó 
  enviar. */
    protected esInvalido(control: string): boolean {
      const c = this.form.get(control);
      return !!c && c.invalid && (c.touched || c.dirty);
    }

    /** Mensaje de error según qué validador falló. */
    protected errorIdentificacion(): string {
      const c = this.form.controls.identificacion;
      if (c.hasError('required')) return 'Este campo es obligatorio.';
      if (c.hasError('pattern')) return 'Solo se permiten números.';
      return '';

    }

  Cómo encaja el pattern field (la parte que querías ver)

  1. Estructura vertical — .field
  Cada bloque es <div class="field">. El pattern le da display:flex; 
  flex-direction:column; gap. Tú no escribes layout: label, control y mensaje se
  apilan solos con el espaciado correcto. Eso es lo que ahorra el pattern
  frente a repetir flex flex-col gap-2 en cada campo.

  2. La etiqueta — .field__label + .field__required
  <label class="field__label" for="identificacion">
    Número de identificación
    <span class="field__required" aria-hidden="true">*</span>
  </label>
  field__label fija tipografía idéntica en TODO el sistema. field__required
  pinta el * en rojo de marca (--app-error). Si mañana cambian el color del
  asterisco, se cambia en un solo lugar.

  3. El control
  Es un componente PrimeNG normal (pInputText, p-select) con formControlName. El
  pattern no toca el input — eso lo maneja el tema de PrimeNG. El pattern solo
  organiza lo que está alrededor.

  4. La joya: .field__message-slot + .field__error
  <span class="field__message-slot">
    @if (esInvalido('identificacion')) {
      <span class="field__error" role="alert">{{ errorIdentificacion() }}</span>
    }
  </span>
  - El slot está SIEMPRE en el DOM, vacío o no. Su min-height reserva el alto de
  una línea. Resultado: cuando el @if muestra el error, nada se mueve — no hay
  salto de layout. Prueba mental: sin el slot, al aparecer el error el botón
  "Guardar" saltaría hacia abajo.
  - field__error pinta el texto rojo y le añade el ícono ⚠ automático vía
  ::before. No pones el ícono a mano.

  5. Ayuda vs error — .field__hint
  El campo "Observación" usa field__hint (texto muted) en vez de field__error.
  Mismo slot, distinto propósito: contexto permanente, no validación.

  El flujo funcional (qué pasa al usarlo)

  1. Cargas el form → los slots ya reservan su espacio, todo cuadrado.
  2. El usuario sale del campo vacío → touched se vuelve true → esInvalido() da
  true → aparece "Este campo es obligatorio." sin mover nada.
  3. Escribe letras → falla el pattern → el mensaje cambia a "Solo se permiten
  números."
  4. Click en "Guardar" con errores → markAllAsTouched() revela todos los
  errores de golpe.
  5. Todo válido → enviado.set(true) y se procesa.

  1. Lo que Tailwind no expresa bien

⏺ Ya tengo todo. Así se maneja la responsividad en tu proyecto: es mobile-first,
  manejada por Tailwind en las plantillas, con una única fuente de verdad de
  breakpoints compartida con el SCSS.

  1. Los breakpoints están definidos UNA vez (y duplicados a propósito)

  Mismos valores en dos sitios, alineados 1:1:

  ┌────────┬────────┬───────────────────┐
  │ Nombre │ Ancho  │       Para        │
  ├────────┼────────┼───────────────────┤
  │ xs     │ 475px  │ móviles grandes   │
  ├────────┼────────┼───────────────────┤
  │ sm     │ 640px  │ móvil → tablet    │
  ├────────┼────────┼───────────────────┤
  │ md     │ 768px  │ tablet            │
  ├────────┼────────┼───────────────────┤
  │ lg     │ 1024px │ desktop           │
  ├────────┼────────┼───────────────────┤
  │ xl     │ 1280px │ desktop ancho     │
  ├────────┼────────┼───────────────────┤
  │ 2xl    │ 1536px │ monitores grandes │
  └────────┴────────┴───────────────────┘

  - En tailwind.css (@theme inline) → para usarlos como prefijos en el HTML.
  - En abstracts/_responsive.scss (mapa Sass) → para usarlos dentro del SCSS.

  Que coincidan es clave: el HTML y el SCSS "rompen" en los mismos puntos, nunca
  se desfasan.

  2. En las plantillas → prefijos de Tailwind (lo normal, el 90%)

  Es mobile-first: la clase sin prefijo es el estado móvil, y el prefijo
  significa "desde este ancho hacia arriba".

  Ejemplo real de tu repo (gestionar-novedades):
  <div class="grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 xl:grid-cols-4 
  gap-5">
  Se lee: 1 columna en móvil → 2 desde sm → 3 desde lg → 4 desde xl. No defines
  "móvil" con media queries; el base ya ES móvil.

  Y en inicio que hicimos:
  class="grid grid-cols-1 lg:grid-cols-[1.15fr_0.85fr] ... lg:p-10"
  class="order-2 lg:order-1"   <!-- imagen arriba en móvil, texto-izq en desktop
  -->

  3. En el SCSS → mixins (solo cuando ya estás en CSS)

  Cuando un estilo vive en SCSS (un pattern, un componente con CSS justificado),
  Tailwind no aplica ahí, así que se usan los mixins:

  @use '../abstracts/responsive' as *;

  .algo {
    @include respond-to(md)    { ... }  // min-width: 768px  (mobile-first)
    @include respond-below(lg) { ... }  // max-width: 1023.98px (desktop-first)
  }

  La regla del propio archivo lo dice: mixins SOLO en SCSS; en el HTML usa los 
  prefijos de Tailwind. Nunca mezclas.

  Lo viste en el shell (app.scss): el drawer empuja el contenido solo en
  desktop, y en móvil queda como overlay:
  @media (min-width: 1024px) {
    &.app-main--drawer-open { padding-left: var(--app-drawer-width); }
  }

  4. Los contenedores resuelven el ancho/padding responsivo por ti

  En vez de teclear max-w-* mx-auto px-4 md:px-6 lg:px-8 en cada página, hay
  clases de layout (@layer layout) que ya lo encapsulan:

  ┌──────────────────┬─────────┬────────────────────────────────────────────┐
  │      Clase       │ Ancho   │                    Para                    │
  │                  │   máx   │                                            │
  ├──────────────────┼─────────┼────────────────────────────────────────────┤
  │ container-app    │ 1280px  │ páginas normales                           │
  ├──────────────────┼─────────┼────────────────────────────────────────────┤
  │ container-fluid  │ 1920px  │ pantallas densas (tablas, filtros) ← la    │
  │                  │         │ usa crear-novedad y novedades              │
  ├──────────────────┼─────────┼────────────────────────────────────────────┤
  │ container-narrow │ 768px   │ formularios / lectura                      │
  ├──────────────────┼─────────┼────────────────────────────────────────────┤
  │ section          │ —       │ ritmo vertical (py) que crece en md        │
  └──────────────────┴─────────┴────────────────────────────────────────────┘

  El padding lateral de estos contenedores ya crece con el viewport (4 → 6 → 8
  en md/lg). Por eso en las plantillas ves class="section container-fluid" y no
  una ristra de utilidades de padding.

  5. Patrón a nivel de componente

  Componentes también adaptan piezas con prefijos. Ejemplo en usuario-menu: el
  nombre/rol se oculta en móvil y solo se ve el avatar (@media (min-width: 
  640px)), para no saturar el header en pantallas pequeñas.

  La regla de bolsillo

  ¿Responsividad en una PLANTILLA?  → prefijos Tailwind (sm: md: lg:),
  mobile-first
  ¿Responsividad dentro de SCSS?    → mixins respond-to() / respond-below()
  ¿Solo es ancho máx + padding?     → usa un container-* (no reinventes)

  Y siempre mobile-first: diseña el estado chico primero, y agrega md:/lg: para
  mejorar hacia arriba — no al revés.

  inicio o el formulario a distintos anchos), o que revisemos si alguna pantalla
  actual tiene un comportamiento raro en móvil?

  no "sabe" nada especial. Solo lee var(--p-primary-50), y las CSS variables se
  resuelven heredando desde :root. Tú cambias ese valor en :root, y la herencia
  hace el resto.

  El mecanismo, paso a paso

  1. PrimeNG escribió sus componentes usando tokens, no colores fijos.
  En @primeuix/themes, el botón no dice background: #2563eb. Dice background: 
  "{primary.color}". Es una referencia simbólica.

  2. El motor de temas compila eso a CSS variables con prefijo p.
  El engine (prefix: "p", selector: ":root,:host") hace dos cosas al arrancar:

  - Toma los valores del preset (los de app.config.ts) y los emite como
  variables en :root:
  :root { --p-primary-50: #eff6ff; --p-primary-color: #2563eb; ... }
  - Convierte las referencias de los componentes en var(--p-...):
  .p-button { background: var(--p-primary-color); }
  .p-button:hover { background: var(--p-primary-hover-color); }

  ▎ {primary.color} → var(--p-primary-color). El {...} se vuelve var(--p-...). 
  ▎ Ese es el "traductor".

  3. Aquí está el truco que no se ve: las CSS variables se HEREDAN.
  Una var(--p-primary-50) no tiene valor propio. Cuando el navegador la
  encuentra en .p-button, busca hacia arriba en los ancestros hasta encontrar
  quién definió --p-primary-50. Como está en :root (el ancestro de TODO), todos
  los componentes la ven.

  4. Tu _primeng-theme.scss redefine esa misma variable en :root... pero en una 
  capa más alta.
  @layer sp-theme {        /* ← capa por encima de 'primeng' */
    :root {
      --p-primary-50: var(--app-primary-50);   /* la línea que marcaste */
    }
  }
  Ahora hay dos definiciones de --p-primary-50 en :root:
  - la del preset (capa primeng): #eff6ff
  - la tuya (capa sp-theme): var(--app-primary-50)

  Como sp-theme gana en la cascada de capas, el valor efectivo de --p-primary-50
  pasa a ser var(--app-primary-50).

  5. El componente, sin enterarse de nada, ahora muestra TU color.
  La cadena de resolución cuando se pinta un botón:

  .p-button  →  var(--p-primary-50)
                     ↓ (resuelve en :root, gana sp-theme)
                var(--app-primary-50)
                     ↓ (resuelve en :root, tokens/_colors.scss)
                #eff6ff

  Por qué esto "cambia los colores de PrimeNG"

  Porque redefinir una CSS variable que ya está siendo consumida cambia, en 
  vivo, todo lo que la lee — sin tocar ni una regla de los componentes. PrimeNG
  escribió var(--p-primary-50) en 100 sitios; tú cambiaste a qué apunta
  --p-primary-50 en un solo lugar (:root), y los 100 sitios se actualizan solos
  por herencia.

  No hay magia ni "PrimeNG detecta el cambio". Es el comportamiento normal de
  las custom properties: valor resuelto en tiempo de uso + herencia desde el
  ancestro.

  La analogía

  Piensa en --p-primary-50 como un interruptor central de la luz:
  - PrimeNG cableó 100 bombillas (var(--p-primary-50)) a ese interruptor.
  - El preset de app.config.ts puso el interruptor en "azul #eff6ff" al
  arrancar.
  - Tu _primeng-theme.scss reconecta el interruptor a tu red eléctrica
  (var(--app-primary-50)), y como tu reconexión tiene prioridad, manda la tuya.
  - Las 100 bombillas no saben nada: solo siguen el interruptor.

  En una frase

  PrimeNG cambia de color porque sus componentes leen var(--p-primary-*), esas
  variables viven en :root, y tu @layer sp-theme redefine su valor con más 
  prioridad → por herencia, todos los componentes resuelven al token --app-*,
  que termina en el hex de _colors.scss.

❯ y por ultimo que es un @layer sp-theme?                                       
  ⎿  ⧉ Selected 1 lines from src/styles/themes/_primeng-theme.scss in Visual Studio Code

⏺ Buena última pregunta, porque @layer es el pegamento de todo lo que hemos
  hablado. Te lo explico desde cero.

  Primero: ¿qué es @layer en CSS? (la función nativa)

  @layer es una característica nativa de CSS (no de Sass ni de Angular) llamada
  cascade layers / capas de cascada. Sirve para controlar quién gana cuando dos 
  reglas chocan, agrupando el CSS en "capas" con un orden de prioridad
  explícito.

  Lo normal en CSS es que gane la regla más específica (un #id gana a una
  .clase, etc.). Eso genera las clásicas guerras de !important. @layer cambia
  esa lógica:

  ▎ Entre capas distintas, gana la capa declarada DESPUÉS — sin importar la 
  ▎ especificidad.

  Ejemplo mínimo:
  @layer base, tema;   /* declaro el orden: base primero, tema después */

  @layer base {
    .boton { color: red; }          /* específico */
  }
  @layer tema {
    div .boton.x.y.z { color: blue; }  /* muchísimo más específico */
  }
  Aquí gana azul, aunque red venga de un selector que normalmente perdería,
  porque tema está después de base en el orden de capas. La capa manda sobre la
  especificidad.

  Segundo: ¿qué es sp-theme?

  sp-theme es simplemente el nombre de una de esas capas. No es una palabra
  reservada: lo eligió tu equipo (probablemente "Salud en casa / Sura Platform 
  theme"). Podría llamarse mi-tema y funcionaría igual.

  Lo importante no es el nombre, sino su posición en el orden que se declara en
  abstracts/_layers.scss:

  @layer reset, base, primeng, sp-theme, layout, components, utilities;
  //                  ▲ antes    ▲ sp-theme va JUSTO después de primeng

  Como sp-theme está después de primeng, todo lo que escribas dentro de @layer 
  sp-theme { ... } gana a los estilos de PrimeNG, sin !important y sin pelear
  especificidad.

  Tercero: por qué eso resuelve tu caso

  Por eso el archivo _primeng-theme.scss envuelve sus reglas en @layer sp-theme:

  @layer sp-theme {
    :root {
      --p-primary-50: var(--app-primary-50);   /* gana a la del preset de 
  PrimeNG */
    }
  }

  Recuerda del paso anterior: PrimeNG define --p-primary-50: #eff6ff en su capa
  primeng. Tú lo redefines en sp-theme. Las dos están en :root (misma
  especificidad), así que el desempate lo decide la capa → gana sp-theme porque
  va después.

  Si no usaras la capa (CSS suelto), tu regla y la de PrimeNG tendrían la misma
  especificidad y el resultado dependería del orden de carga — frágil. Con
  @layer, el ganador está garantizado por diseño.

  La pieza que conecta con app.config.ts

  Para que esto funcione, PrimeNG debe inyectar sus estilos dentro de la capa 
  primeng. Eso se le dice en app.config.ts:

  providePrimeNG({
    theme: { options: { cssLayer: {
      name: 'primeng',
      order: 'reset, base, primeng, sp-theme, layout, components, utilities',
    }}}
  })

  Ese order debe ser idéntico al de _layers.scss. Si difieren, PrimeNG queda
  "fuera de capa" y toda la prioridad se rompe. Por eso hay un comentario que lo
  advierte en ambos archivos.

  Resumen en 3 frases

  1. @layer es CSS nativo para ordenar prioridades por capas, no por
  especificidad: gana la capa declarada de último.
  2. sp-theme es el nombre de la capa de overrides de tu proyecto, colocada
  justo encima de primeng para ganarle siempre.
  3. Por eso, redefinir --p-primary-50 dentro de @layer sp-theme vence a la
  definición de PrimeNG de forma garantizada, sin !important.

  ▎ Analogía: las capas son como pisos de un edificio. La especificidad decide 
  ▎ quién manda dentro de un piso; pero entre pisos, siempre manda el piso de 
  ▎ arriba. utilities (Tailwind) es la azotea (máxima prioridad), sp-theme está 
  ▎ un piso por encima de primeng, y reset es el sótano.

  Con esto cierras el modelo completo: tokens (la verdad) → @theme/var() (los
  conectores) → @layer (quién gana) → main.scss/angular.json (quién carga y
  ordena). ¿Quieres que agregue esta explicación de @layer sp-theme a la página
  HTML de documentación para tenerlo todo junto?

  Lo que NO reescribe (y no puede, por diseño)

  1. La estructura/geometría/comportamiento del componente.

  cambiar el markup interno, alterar cómo se posiciona un overlay o reescribir
  la lógica de animación. Eso no son variables --p-*, son reglas CSS reales de
  PrimeNG. Para tocarlas necesitarías CSS de verdad (no reasignación de token).

  2. Lo que no esté expuesto como token --p-*.
  Si PrimeNG no expuso una variable para cierto detalle, sp-theme no lo alcanza.
  Tendrías que escribir una regla específica (idealmente también dentro de

  radios particulares) se quedan con los valores del preset de Lara definido en

  matices.

  4. El origen del color.
  sp-theme no define colores; los toma de tokens/_colors.scss vía var(--app-*).
  Si quieres cambiar el azul, vas a _colors.scss, no aquí.

  5. Nada fuera de PrimeNG.
  No toca Tailwind, ni los patterns (.card, .field), ni el CSS de tus
  componentes. Su único universo son las variables --p-*.
